Охват: src/server/app.ts (onRoute/AsyncLocalStorage), store.ts (чтение/запись/настройки), workspace.ts (серверная сессия), routes/auth.ts, demo.ts, intelligence.ts (два raw SQL scheduler-запроса), tests/demo.test.ts. ## Результат

Блокирующих утечек между демопрофилями и обычными аккаунтами в проверенном потоке не обнаружено. Scope извлекается из серверной Redis-сессии, а не запроса пользователя; get/list/remove/upsert ограничены scope; текущий аккаунт загружается без scope только по Redis user id. Настройки получают отдельное пространство ключей. Создание и login обычных аккаунтов выполняются вне демоскопа. Оба прямых запроса scheduler исключают демоверсии; фоновые Store без scope не обрабатывают демозаписи. S3 download проходит через scoped version и проверку документа.

Независимо выполнено `RUN_INTEGRATION=1 INTELLIGENCE_WORKER_ENABLED=0 bun test tests/demo.test.ts`: exit 0, 1 pass, 0 fail, 28 assertions. Использованы реальные локальные PostgreSQL/Redis/MinIO и временная БД, которую тест удалил. Проверены приватность документов/оригиналов/шаблонов, ограничение ролей, отсутствие демоданных в обычном workspace, запрет записи в чужой scope и компенсация S3 при частичном отказе. Тест последовательный: отдельной проверки конкурентных ALS-контекстов в нём нет.

## Замечание к исправлению

Низкая важность: `src/server/demo.ts` задаёт номенклатуре поле `number: "02-14"`, но `src/client/features/ProfileFields.tsx` читает `c.code`; публичный Bootstrap тип также содержит `code`. В результате в демоформе отсутствует номер дела. Исправление: использовать `code`, как ожидает потребитель. Передано основному агенту; сам backend не менял.

## Границы и эксплуатационные ограничения

- Факт: Redis-сессия истекает через сутки, но PostgreSQL/S3 демоданные не удаляются. Новый вход постоянно увеличивает объём; автоматическая очистка в этой реализации отсутствует. Нельзя описывать TTL сессии как удаление документов. Политика хранения требует отдельного решения, если демо будет долго публично работать.
- Факт: Fastify создаётся без trustProxy, rate limiter использует request.ip. Предположение: на Railway запросы разных посетителей могут иметь один адрес прокси; тогда лимит 30 запусков/минуту разделяется ими. Конфигурация реального edge не проверена; нельзя бездумно доверять произвольному X-Forwarded-For. Перед публикацией нужно проверить проксирование и настроить доверие только к известному proxy при необходимости.
- Каждый новый демовход заменяет cookie текущего браузера; параллельные вкладки используют последнюю сессию. Серверные записи остаются разделёнными, но профиль вкладки не имеет отдельного cookie namespace. Это следствие browser session semantics, а не доказательство доступа к чужому пользователю.
