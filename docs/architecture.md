# Архитектура

Solid UI разделён по ответственности: main монтирует App; AppProvider хранит reactive state/API operations/navigation; WorkspaceShell отвечает за layout; components — общие элементы; features — реестр, профиль, настройки и карточка; features/document — отдельные вкладки. Компоненты находятся на уровне модулей и получают данные через типизированные props/context. HTTP клиент и типы отделены. Tailwind @theme/@apply и utilities задают общие токены/геометрию исходного UI.

Fastify index только запускает createApp. app собирает сервисы/hooks/errors/routes; routes разбиты по предметным API. domain содержит валидацию, document-service — запросы/операции документов, workspace — аккаунты/профили/сессии; store/schema — Drizzle через Bun SQL. Оригиналы — MinIO через Bun S3Client; сессии — Bun RedisClient; пароли — Bun.password. Worker Ollama отдельный от HTTP-модулей.

Документ: HTTP → session/validation → Drizzle/PostgreSQL; файл → проверка формата/размера → S3 → неизменяемая версия PostgreSQL → UI. Клиент не выбирает автора загрузки. S3/PG не имеют общей транзакции, поэтому ошибки компенсируются. Правила ИИ пусты до реальной настройки, ошибки не превращаются в положительный отчёт.

Папку templates backend не читает. Это только MD/TXT образцы; пользователь вручную загружает документ из своего профиля. Личные шаблоны реквизитов — отдельная доменная сущность PostgreSQL. Автоматических seed или mock adapters в runtime нет.

Vite нужен для специализированной компиляции Solid JSX и Tailwind, результат dist отдаётся Fastify на том же origin. Compose содержит только PostgreSQL, Redis, MinIO и bucket init. Railway — Bun/Railpack вне локального Compose, [параметры](railway.md).

Дальнейшие изменения можно делать в отдельных feature/route modules. Корпоративный identity provider и OCR сканов ещё не реализованы. Legacy импорт требует сопоставления владельцев с реальными аккаунтами и резервной копии. Тесты используют временные БД и объекты, не рабочие данные.

Обследование c51161e и продолжение 29.10.2026: extraction.ts извлекает текстовые PDF/DOCX с лимитами ресурсов; intelligence.ts выполняет проверку цитат, фоновые задания с Redis lease и run_id, хранит факты/векторы в JSONB отдельно для каждой версии. routes/intelligence.ts проверяет роль куратора для обзора, сводки и повторной обработки; смысловой поиск фильтрует документы по владельцу до чтения версий. Хеши файла и текста связывают индекс с источником. Knowledge.tsx показывает поиск и кураторский обзор. Автоматические результаты не изменяют согласование. Подробно просмотрены этот поток, маршруты и проверки; это не полный аудит остальных модулей. Реальный Ollama в текущем окружении недоступен.

## Приватное демо

`routes/auth.ts` → `demo.ts` создаёт вымышленный профиль и небольшой набор документов в транзакции, оригиналы TXT в S3; при сбое создания выполняется компенсация объектов. `app.ts` оборачивает API handlers в `demoScope` (AsyncLocalStorage), полученный из серверной сессии. `Store` фильтрует записи по JSONB `demo_id` на SQL-уровне и отделяет настройки префиксом пространства. Обычные запросы не видят демозаписей, включая кураторские; `currentUser` делает единственное явное чтение аккаунта вне scope по Redis-сессии. Фоновые intelligence SQL-запросы исключают demo; проверка ИИ не имитируется. Схема не меняется. Автоматическая очистка демодокументов пока не реализована: истечение Redis-сессии не удаляет PG/S3.

Клиент `app-store.tsx` запускает демо при полной загрузке, очищает старую ссылку на документ и затем читает bootstrap. `/login` сохраняет обычную авторизацию и завершает прежнюю демосессию перед показом формы. `/demo` рендерится без AppProvider и не создаёт профиль. `DemoPage.tsx` кодирует текущий origin библиотекой qrcode-generator локально в SVG; данные не передаются сервису генерации QR. Мобильный реестр использует те же записи и обработчики, меняется только представление таблицы в карточки. Обследованы затронутые API/storage/session/worker и UI потоки; это не полный аудит приложения.
